# 月次KPI更新手順

毎月の楽天売上分析(KPI管理シート)の更新フロー。原価は商品マスターに一元管理する。

## 月次標準フロー(2026-09-08 確定)

**分析で終わらせない。商品マスターを最新の正本にするところまでが1か月の作業である。**

```
⓪ 列構成チェック  各スクリプトが実行の最初に自動で行う(人の操作は不要)
      ↓          前月と違えば差分を表示して**停止する**。詳細は下記
① 分析          売上(楽天→Amazon)→ 手数料実額化 → 広告(楽天→Amazon)
      ↓          ⚠️ 広告はKPIシートの同月を読むため、売上より後でなければ動かない
② 要対応一覧を確定 python3 build_todo_lists.py <月> <Transaction.csv>
      ↓          読み取り専用。修正する順番で7一覧を出力し、人が中身を確認する
③ register      python3 sync_cost_master.py register <月> / register-amazon <月>
      ↓          ★ユーザーの承認が必要。実行前に商品マスターのバックアップを取る
      ↓          原価不一致があれば adopt / adopt-amazon も同様に承認のうえ実行
④ 月次経費を入れる python3 apply_monthly_expenses.py ad <月>   ← 広告費の額を算出
      ↓          python3 apply_monthly_expenses.py list <月> → set ...
      ↓          広告費はAIが①から算出。それ以外は人が請求書・RMS等から転記
      ↓          **すべて埋まって初めて限界利益が確定する**
⑤ 広告改善一覧    python3 build_ad_actions.py <月> <前月>
      ↓          全商品を 即停止候補/停止テスト/増額/テスト/継続 に分類
      ↓          ★実行は人が判断。**アトリビューション成熟度を必ず確認する**(下記)
⑥ 一覧を再生成    ②をもう一度実行する
```

**①②③の順番は固定である。** 入れ替えてはならない。

| なぜこの順番か | |
|---|---|
| ②が③より先 | `register` はマスター(正本)を書き換える。何を登録するのかを人が見てから走らせる |
| ④が③の後 | 原価が入ると粗利率が変わる。⑤の損得判定はその粗利率を使う |
| ⑤が④の後 | 改善率の分母が限界利益。経費が入っていないと分母が出ない |
| ⑥が最後 | 登録した商品は中身が空のまま入る。再生成して初めて「次に何を直すか」が見える |
| ①が②より先 | 一覧はKPIシートの当月実績(出荷数・売上)で優先順位を決めるため |

> ④⑤ は 2026-09-08 に追加した。8月を実際に通して、
> 「広告費をKPIへ入れる」「広告の止める・増やすを判定する」工程が
> フローから抜けており、手作業になっていたため。

⑥は「改善したか」を数字で確かめる場でもある。**再生成したときに件数が減っていることをもって、改善したと判断する。**

> ⚠️ **広告費の税の扱いはチャネルで違う。**
> 楽天はRPPの「割引後実績額」が税抜で、KPIシートは**税込**で持つ慣例
> (4月143,000 / 5月132,680 / 6月75,246 / 7月76,791 はいずれも税込)。
> Amazonはレポートの費用を**そのまま**入れる。
> 2026-09-08 にこの違いを見落として楽天へ税抜を入れる誤りをしたため、
> **`apply_monthly_expenses.py ad <月>` が正しい額を算出する**ようにした。
> 手計算せず、このコマンドの出力を使うこと。

## OS共通原則: 0 / 空欄 / 未取得 / 未確認 / 未確定 は別状態(2026-09-09 確定)

**この5つを同一視しない。** 2026-09-09 の監査で、5領域すべてで混同が見つかった。

| 状態 | 意味 | 例 |
|---|---|---|
| **0** | **値である。**「無い」ことを測って確かめた結果 | 在庫を数えて0だった / クーポン利用額が実際に0円 |
| **空欄** | まだ入力していない | KPIシートの送料が未入力 |
| **未取得** | データ自体を取りに行っていない | 在庫リストを今月まだ落としていない |
| **未確認** | 値はあるが人が検証していない | システム在庫はあるが棚卸していない |
| **未確定** | 時間が経てば確定するが、まだその時ではない | 楽天RPPの720時間アトリビューション |

### 実装で守ること

- **0で埋めない。** 値が無いなら `None` を通し、集計から外すか「算出不能」と出す
- **Excelの空セルは0として集計される。** 数式にガードを入れる（限界利益の `COUNTBLANK`）
- **確定しないものには基準日・成熟日を併記する**
- 判定ロジックは `in (None, '')` と `== 0` を書き分ける

> 原価だけは例外として当面 `in (None, '', 0)` のままとする(2026-09-09 承認I)。
> 原価0円の商品が現状存在しないため。**発生したらロジックを変更する。**

### 経費項目にも徹底する

| 入れ方 | 意味 |
|---|---|
| **0 を入力する** | 確認したうえで本当に0円だった（例: 8月のクーポン利用手数料） |
| **空欄のまま** | まだ入力していない |

**「今月は無かったから空欄でいい」は誤り。** 0 と入力してください。
空欄のままだと限界利益が「未確定」になり、確定した月と区別が付かなくなります。

### 在庫金額の扱い(2026-09-10 確定)

**評価方法の違う金額を直接統合しない。** 表示するときは必ず
**基準日**と**評価方法**を併記する。

| 金額 | 基準日 | 評価方法 | 用途 |
|---|---|---|---|
| ¥20,597,070 | 2026-08-03 | CSV単価（モールの在庫リストに載っている単価） | 全体在庫サマリーの実績値 |
| ¥22,572,096 | 2026-08-03 | 標準原価（商品マスター E列） | 棚卸対象リストの参考値 |

**経営管理用の参考在庫金額は「システム在庫数量 × 標準原価」を使う。**
原価の正本が商品マスターであり、KPIの粗利計算と物差しが揃うため。

> ⚠️ どちらも **2026-08-03 時点**であり現在在庫ではない。
> ⚠️ 標準原価が無い商品（290件）は金額0で計上されるため、合計はその分だけ過小。

### 棚卸の進め方(2026-09-10 確定)

**290件の原価なし在庫を先に全部調査しない。** 順番を守る。

```
① 最新在庫データの取得（RMS / セラーセントラル）
      ↓
② 実地棚卸（要対応一覧 07_棚卸対象リスト の順に数える）
      ↓
③ 実在庫あり商品の確定（棚卸入力シートへ記録）
      ↓
④ 「在庫あり × 原価なし」の商品だけを優先的に原価補完
```

④で対象が絞れる。実在庫が無い商品の原価を調べても意味がない。

## 原価の突合: 単位を揃えてから比べる(2026-09-10 確定)

**マスターの標準原価とKPIの仕入値は、単位が違うことがある。**
引き算する前に、その2つが同じものを指しているか確かめる。

### 単位はどこに持つか

**出品(ASIN/SKU)単位**で持つ。商品マスターには持てない。
同じ内部管理IDに入数の違う出品がぶら下がっているためである。

実例: P000225 肌ラボ — **楽天は3本セット、Amazonは単品**を同じIDで売っている。

| チャネル | 識別子 | 平均単価 | KPI仕入値 | 商品名 |
|---|---|---:|---:|---|
| 楽天 | b0c656jxkd | ¥3,980 | 2,283 | 140ml**×3** |
| Amazon | B08WS9L34F | ¥1,450 | 761 | 140ミリリットル **(x 1)** |

出品テーブル(末尾3列):

| 列 | 名前 | 入れる値 |
|---|---|---|
| L | 販売入数 | この出品が単品いくつ分か。正の整数。**空欄=未確認** |
| M | 原価単位 | `単品原価` / `セット原価`。**空欄=未確認** |
| N | 確認根拠 | 何の資料で何を確認したか、対象時点まで書く |

### 確認のしかた

| 項目 | 何で確認するか |
|---|---|
| **販売入数** | 対象月の**出品情報・注文情報**（Amazonカタログのタイトル、楽天の商品名など） |
| **原価単位** | **仕入明細**と**マスター登録根拠** |

> 🚫 **納品書の日付だけで「確認済み」にしない。**
> 確認根拠には「何の資料で・何を・いつ時点で」確認したかを書く。
> 例: `2026-08 Amazon出品情報のタイトル「(5袋)」で販売入数5を確認(確認日2026-09-10)`

> 🚫 **原価の比率が整数に乗ることを単位一致の証拠にしない。** 倍率は参考情報にすぎない。

### 対象証憑の期間

**8月の原価確認で見るべきは「8月の仕入分」ではなく、
「8月に売れた分の原価根拠となる仕入分」である。**
先月以前に仕入れた在庫が8月に売れていれば、その仕入の明細が根拠になる。

### セット原価を使ってよい条件

`セット原価` は、**マスター原価の対象構成と出品の構成が同じと確認できた場合だけ**。

- 付属品付き（おしぼり付きなど）
- 異種混合セット（味違いのアソートなど）

は、**原価の含有範囲まで確認できなければ保留**（空欄のまま）。

### 揃えられないときにどうするか

「単位未確認」として扱い、**差額・利益への影響額を出さない**。
元のKPI値とマスター値は表示する。合計にも入れない。

- `02_原価確認` … 差額欄に「単位未確認」と出し、影響額は空欄
- `push-kpi` … 更新対象から除外。**反映側でも弾く**

さらに `push-kpi` の反映には **更新理由「入力ミス」の記入**が要る。
**現在の標準原価と違うというだけで過去月を更新しない。**
仕入価格が変わっただけなら、その月はその原価で売っている。

### KPI生成が原価を「採用」する条件と、確認根拠(N列)の書き方(2026-09-12 確定・Y-1/Z-4)

原価の出所は3つ。**どれも「値があるだけ」では採用しない。** 採用できなければ L列は空欄(黄色)のまま、
P列に「原価未確定: 理由 / 参考候補: 7月 L=1,287」のように残す。**参考候補は確定原価欄を埋めない。**

| 出所 | 採用の条件 |
|---|---|
| ① マスター×入数 | 出品テーブルの 販売入数・原価単位 が記録済み(従来どおり) |
| ② RMS商品番号(`RMS_COST=1` のときだけ・既定OFF) | 明記型 ＋ 出品が管理番号×SKUで一意 ＋ N列に `含有範囲=確認済み…` ＋ N列の `RMS原価対象月` が生成月を含む ＋ 番号から読める構成が出品テーブルと矛盾しない |
| ③ 過去月シート | 同じ出品(管理番号×SKU)で一意 ＋ 商品番号が同一か番号から読める構成・入数が一致 ＋ 過去行のP列の根元の出所が確認済み(マスター×入数／RMS(条件付き)／人が確認) ＋ N列に `原価継続=可(…)` |

**確認根拠(出品テーブルN列)には自由記述の中に `項目=値` を書く**(区切りは `/` か改行)。文字が含まれるだけでは読まない。

```
含有範囲=確認済み(付属品なし)           ← 「含有範囲」の文字だけ／「未確認」「資料待ち」は不可
RMS原価対象月=2026-08〜                  ← 〜は以降ずっと。2026-08,2026-09 の列挙も可
原価継続=可(2026-09-12確認)             ← この出品の確認済み原価を後の月へ引き継いでよい
```

⚠️ P列に出所メモが無い過去月の値(2026-09-11 より前に作ったシート)は、人が入れたのか自動で引き継いだのか
区別できないため**確認済みとは扱わない**。8月をこの条件で作り直すと 262行中 261行が未確定になる
(2026-09-12 コピーで測定。本番の8月シートは変更していない)。

## 既知事項: 楽天5月シートの残骸(2026-09-09 確認 / 対応しない)

## アトリビューション成熟度の確認(2026-09-09 追加)

**広告の「売上0」は、成熟していないチャネルでは「まだ売上が付いていない」だけかもしれない。**
これを見落とすと、これから売れる広告を止めてしまう。

| チャネル | アトリビューション | 月末クリックの確定日 |
|---|---|---|
| Amazon SP | 7日 | 月末 + 7日 |
| 楽天 RPP | 720時間(30日) | **月末 + 30日** |

`build_ad_actions.py` が実行時に自動で判定し、未成熟なら:

- 「売上0」を **即停止候補ではなく「停止テスト」** に分類する
- 確信度を **必ず「低」** に落とす

**楽天は月初にレポートを取っても必ず未成熟である。**
8月分を確定させるには **2026-10-01以降** に再取得して再判定する。

> 実例: 2026-09-09 時点の8月分析では、停止による改善額 ¥30,931 のうち
> ¥27,421(89%)が未成熟な楽天だった。承認できたのは成熟済みAmazonの ¥3,510 のみ。

## ⓪ 列構成チェック(2026-09-08 確定)

2026-09-08、Amazonビジネスレポートから `SKU` 列が消え、以降の列が1つずつ左へずれた。
固定の列番号で読んでいたため、売上・個数・注文数がすべて隣の「- B2B」列を指し、
**8月売上が ¥5,610,675 → ¥227,580 と誤って集計された。** 売上が落ちたのではなく、
読み取りが壊れていた。二度と起こさないための関門である。

**人が操作することは何もない。** 各スクリプトが起動直後に自動で行う。
バックアップより先に走るので、壊れたレポートで作業を始めることがない。

| 状況 | 動き |
|---|---|
| 前月と同じ | `前回(8月)と同じ 21列 ✓` と出して続行 |
| 初回 | その構成を記録して続行 |
| **列が増えた・減った** | **追加/削除された列**と**現在の見出し一覧**を出して**停止**(終了コード1) |
| **並び順だけ変わった** | どこが入れ替わったかを出して**停止**(終了コード1) |

止まったら、差分を確認したうえで受け入れる:

```bash
ACCEPT_LAYOUT=1 python3 build_amazon_kpi_month.py ../SourceData/BusinessReport-XX.csv 9月
```

受け入れた構成は `02_Analytics/Python/column_layouts.json` へ履歴付きで記録される
(BL-7 記録なき変更を認めない)。Git管理下なので**いつレポート仕様が変わったのかを後から遡れる。**

> 🚫 **見出しを部分一致で引かないこと。**
> 「セッション数 - 合計」は「セッション数 - 合計 - B2B」にも含まれる。
> 部分一致にすると B2B 列を掴み、上記の事故がそのまま再現する。完全一致だけを使う。

**対象スクリプト(すべて `report_columns.py` を経由する)**

| スクリプト | レポート |
|---|---|
| `build_kpi_month.py` | 楽天 SKU別売上CSV |
| `build_amazon_kpi_month.py` | Amazon ビジネスレポート |
| `build_rakuten_rpp_month.py` | 楽天RPP 商品別 / サマリー |
| `build_amazon_sp_month.py` | AmazonSP 広告対象商品 / 検索用語 |

※ 商品マスター・出品テーブル・在庫リストは**自社が形を決めているファイル**なので
この仕組みの対象外。列は末尾へ追加する運用で守る(`Master_Design.md`)。

## 前提

- 対象ファイル: `02_Analytics/SourceData/楽天運営 KPI管理シート.xlsx`
- 原価の正: `01_InventoryManagement/SourceData/商品マスター_単品_v1.0.xlsx`

## 毎月の手順

```
cd MomijiStore_OS/02_Analytics/Python
```

1. **RMSからCSVをダウンロード**
   データ分析 → SKU別売上 → 対象月で絞ってCSVダウンロード
   (ファイル名例: `202608_SKU_SalesList.csv`)。`02_Analytics/SourceData/` に置く。

2. **月次シートを生成**
   ```
   python3 build_kpi_month.py ../SourceData/202608_SKU_SalesList.csv
   ```
   - シート名はファイル名から自動判定(`202608` → `8月`)
   - バックアップ取得 → シート生成 → Excel再計算 → CSVとの合計突合まで自動
   - 仕入値は 商品マスター → RMS埋め込み → 過去月 の順で解決。未解決は黄色塗り

3. **黄色セルを入力**
   - 仕入値が未解決の行(新商品)
   - 月次経費: 広告費・ポイント費用・クーポン利用額・送料・梱包資材
   - 入力後にExcelで保存すれば限界利益・限界利益率が確定

4. **新商品をマスターへ還流**
   ```
   python3 sync_cost_master.py register 8月
   ```
   - 未登録の商品を商品マスター+出品テーブルへ追加登録
   - 原価不一致が表示されたら内容を確認し、KPI側に合わせてよければ
     `python3 sync_cost_master.py adopt 8月`

5. **在庫集計ツールへ配信**
   ```
   python3 sync_cost_master.py push
   ```
   - 商品マスターの原価を在庫金額集計ツールの「原価マスター」シートへ反映
   - 以後、在庫集計の原価未登録(要確認一覧)が減る

## Amazon(ビジネスレポート)

1. セラーセントラル → ビジネスレポート → 詳細ページ売上・トラフィック(子商品別)
   → 対象月で期間指定してCSVダウンロード
2. ```
   python3 build_amazon_kpi_month.py ../SourceData/BusinessReport-XX-XX-XX.csv 8月
   ```
   - 出力先: `Amazon運営 KPI管理シート.xlsx`(月別シート)
   - 仕入値の照合順: 商品マスター(ASIN→AmazonSKU) → Amazon在庫リスト
3. 手数料の実額化: トランザクションレポート(ペイメント → レポートリポジトリ → 月指定)
   をダウンロードして
   ```
   python3 apply_amazon_fees.py ../SourceData/2026XxxMonthlyTransaction.csv 8月
   ```
   - K列(販売手数料)をSKU別実額に置換(同一SKU複数行は売上比で按分)
   - プロモーション費・その他手数料・送料も自動入力
4. 残りの黄色セル(仕入値・広告費・梱包資材)を入力して確定
5. 新商品をマスターへ還流 → 在庫集計ツールへ配信
   ```
   python3 sync_cost_master.py register-amazon 8月
   python3 sync_cost_master.py push
   ```
   - 原価不一致が出たら内容確認のうえ `adopt-amazon 8月`(ユーザー承認必須)

## 楽天RPP広告分析

1. RMS広告センター(プロモーション → RPP)から月次レポート2種をダウンロード
   - 商品別レポート(`rpp_item_reports_...csv`)/サマリー(`rpp_reports_...csv`)
2. ```
   python3 build_rakuten_rpp_month.py ../SourceData/rpp_item_reports_xxx.csv ../SourceData/rpp_reports_xxx.csv 8月
   ```
   - 出力先: `楽天RPP広告分析.xlsx`(月別シート)
   - KPIシートの同月と結合し広告依存度・広告費対粗利を算出(KPIシート生成後に実行)
   - KPIシート経費欄の広告費 = RPP割引後実績額の税込(×1.1)

## AmazonSP広告分析

1. 広告コンソール → 測定と報告 → スポンサー広告レポートで2本作成(期間は対象月、時間単位: 概要)
   - レポートタイプ「広告商品」(必須)/「検索用語」(任意)
2. ```
   python3 build_amazon_sp_month.py "../SourceData/広告対象商品レポート.xlsx" 8月 "../SourceData/検索用語レポート.xlsx"
   ```
   - 出力先: `AmazonSP広告分析.xlsx`(月別+<月>_検索用語シート)
   - Amazon KPIシートの同月と結合(KPIシート生成後に実行)
   - アトリビューションは7日間(楽天RPPの720hと基準が異なる)
